# Project conventions

The current roadmap (what's done, what's next, open questions) is in `docs/PLAN.md`; read it at the start of a session and keep it updated. Real iCal exports for tests go in `fixtures/ical/` (scrubbed, see its README).

Hallgatói réteg: a per-course dashboard that sits on top of university systems (Neptun, Teams, Canvas, Moodle, TMS, Discord…).

- **Language:** all UI text is Hungarian; code, identifiers and comments are English. Routes are Hungarian (`/`, `/targy/[id]`, `/radar`, `/beallitasok`).
- **Accounts (server is the source of truth):** sign-in is required (email + password, or magic link; the email must be confirmed). Hand-rolled auth on `node:crypto` (`lib/server/auth/*`: scrypt, tokens stored as sha256, `hr_session` httpOnly cookie, Origin check on mutating routes) behind the `AccountStore` interface (`lib/server/account/store.ts`; `memoryStore` for dev and tests, `redisStore` for Upstash; records and keys in `docs/superpowers/specs/2026-10-05-accounts-design.md`). Routes: `/api/fiok*` (register, sign-in, links, password, email, delete; `/api/fiok/naptar`, `/api/fiok/hirlevel`), `/api/adatok` (one versioned data document per user, compare-and-set, 409 returns the remote). `proxy.ts` redirects app pages without a session cookie to `/belepes` (optimistic only; the API is the real gate). The client keeps the zustand store `lib/store.ts` as the in-memory model and a localStorage cache (`hallgatoireteg-v2`, with `ownerUserId`); `components/AccountSync.tsx` + `lib/sync/*` push debounced changes and pull on focus, merging three-way on conflict (`mergeAppData`). Types are in `lib/types.ts`. Select slices individually: `useStore((s) => s.courses)`. Storage and Resend are needed in production (503 without).
- **Hydration:** components that read the store are client components and render a skeleton until `useHydrated()` (`lib/useHydrated.ts`) returns true for device preferences, or `useDataReady()` (`lib/useDataReady.ts`) once the store holds this user's data.
- **Dynamic routes:** `page.tsx` is a thin server component that awaits `params` (typed with `PageProps<"/route/[id]">`) and renders a client component (e.g. `app/targy/[id]/page.tsx` → `components/week/CourseWeekDetail.tsx`).
- **UI:** Tailwind v4 with the color tokens from `app/globals.css` (`bg-card`, `border-border`, `text-muted`, `bg-accent`, `text-danger`…). Build from `components/ui/*` and use `lucide-react` icons. No component libraries, and no new dependencies without asking.
- **Platforms:** built-in platforms are in `lib/platforms.ts`, and user-defined ones in `customPlatforms`. Always resolve them with `getPlatform(id, customPlatforms)`. Normalise user URLs with `normalizeLinkUrl` (`lib/url.ts`).
- **Deadlines:** urgency, week grouping and the weekly summary are pure functions in `lib/radar.ts` (weeks start on Monday). Reuse them; don't recompute urgency in components. Deadlines with `source: "ical"` can't be edited or deleted, only marked done or critical.
- **iCal:** `app/api/ical/route.ts` is a CORS proxy (fetching lives in `lib/ical/fetch.ts`, shared with the subscription routes). Every URL, and every redirect hop, must pass `assertPublicUrl` (`lib/ical/ssrf.ts`); never remove that check or switch to `redirect: "follow"`. Parsing (`lib/ical/parse.ts`) and course matching (`lib/ical/match.ts`) are pure functions. Sync goes through `lib/ical/client.ts` → the store's `applyFeedSync` (a thin wrapper over the pure `mergeFeedSync` in `lib/ical/sync.ts`, also used by the server), which upserts by `(feedId, externalUid)` and keeps the user's `done`/`critical`/course choices. Canvas context parsing lives in `lib/ical/canvas.ts`, discovery in `lib/ical/discover.ts` + the store's `applyDiscovery`; every sync also runs `autoLinkContexts`, which adds a context's Canvas course link to the course it already belongs to (fixed course or keyword match) once, remembered in `IcalFeed.linkedContexts` so a deleted link stays deleted; matching is longest-keyword-wins.
- **Search & quick-add:** search lives in `lib/search.ts` + `components/CommandPalette.tsx`, the quick-add parser in `lib/quickAdd.ts`; matching is accent-insensitive via `normalizeSearch` (`lib/text.ts`).
- **Dialogs:** `components/ui/Dialog.tsx` mounts its children only while open, so forms inside it initialise from props with `useState(initial…)`.
- **Design system:** "Hirdetőtábla" (faculty notice board), in daylight (light) and after hours (dark). Tokens in `app/tokens.css`, one block per theme on `[data-theme]` (light is `:root`); hover tints use `bg-wash/[…]`, never `bg-black/…`; shadows, backdrop and canvas inks are tokens too. The preference (`theme`: system | light | dark, default system) is a store device preference, applied before paint by `THEME_SCRIPT` (`lib/theme.ts`) in the root layout and kept in sync by `ThemeSync`; toggle in the header (`ThemeToggle`) and Beállítások → Megjelenés (felt `--bg`, copy-paper `--panel`, toner `--accent` for primary buttons and active controls with `text-accent-ink` on it, red `--pin` / `--danger` only for now, late, critical and destructive, coloured papers `--canary` (today, highlight), `--salmon` (overdue), `--sky` (classes)), mapped to Tailwind colours in `globals.css`. Font: Archivo via next/font; headings use `.font-display` (condensed, heavy). Primitives in `globals.css`: `.pin` (round head, colour via `--pin-color`), `.slip` (a pinned paper slip; `data-done` unpins and tilts it), `.sheet-paper`. Deadlines on boards are `DeadlineChip` slips whose pin carries state (course colour, red when hot, gone when done). Pages use `SectionHeading` (title + optional sub + actions; no eyebrows or kickers), `Card`, `Pill`, `Dialog`, `EmptyState` from `components/ui/`; `PinboardField` is the canvas background (one faint slip per open deadline, each in a fixed slot; ticking off takes the latest down, unticking or adding pins one up). No raw hex outside user/course/platform data and `PinboardField`; no gradients, glows or glass; copy is concise, professional Hungarian with no jokey asides; respect `prefers-reduced-motion`.
- **Calendar subscription (account-owned, opt-in):** `buildCalendar` (`lib/ical/export.ts`, pure, ical.js) renders one merged .ics; `downloadCalendar()` does it in the browser with no server. Turning the subscription on creates a public read-only **token** (`/api/fiok/naptar`, stored as `sub:<token>` → `{ userId }` and on the user; `?uj=1` rotates, DELETE turns off); there is no secret and no snapshot upload: the server renders from the account's data document. `GET /api/naptar/[token]` (public) → `renderCalendar(store, userId, now, appUrl, view)` in `lib/server/calendar.ts`, which builds the input with `calendarInput(doc)` (`lib/server/calendarInput.ts`: course links/resources stripped, timetable via `visibleSessions`, capped at 1500), re-fetches the source feeds through `loadLiveDeadlines(kv, userId, input, now)` (cache `src:<userId>:<feedId>`, 15 min), merges with `mergeFeedSync`, warns about feeds failing > 24 h, and caches the result as `ics:<userId>:<view>` (15 min, listed in `icsk:<userId>`); every successful data save (`saveData`) deletes those, so edits show at once. Views: `?nezet=osszes|kritikus|zh|orarend|targy-<courseId>` (`lib/ical/views.ts`, unknown → everything); `buildCalendar` also adds opt-in-by-default `weeklySummary` (all-day "Heti radar" on the Monday of 4 weeks) and `studyBlocks` (2 all-day days before open critical deadlines), both transparent; `ExportOptions` live in the data document and are defaulted by `validateExportOptions`. A feed-reported due change sets `previousDue`/`dueChangedAt` in `mergeFeedSync` and shows `módosult` for 48 h (`isRecentlyChanged`). `IcalFeed.markDoneBefore` makes deadlines created by a sync that were already past done. Everything date- or week-dependent in exports uses the Budapest helpers in `lib/ical/budapest.ts`, never the runtime's local time (the server is UTC). iCal UIDs derive from `feedId` + `externalUid`, never from deadline ids.
- **Duplicates:** `lib/ical/dedupe.ts` (pure) finds the same deadline from several sources: different feeds (or manual + feed), same course, same Budapest day (±60 min when both are timed), similar titles (whole-token containment or token overlap ≥ 0.6, number guard so "Beadandó 02" ≠ "03"). Groups are **computed, never stored**; only the user's exceptions live in `AppData.ignoredDuplicatePairs` (pair keys of `deadlineIdentity`, which is `ical:<feedId>:<externalUid>` or `manual:<id>`, never the random server-side id). Primary by source priority manual > canvas > moodle > neptun > other. `ExportOptions.dedupe` (default on) governs the app lists too: use `useDedupedDeadlines()` (`lib/useDedupedDeadlines.ts`) for anything that lists or counts deadlines; `buildCalendar` dedupes before filtering the view and adds a "Források:" block. `toggleDone`/critical on a primary apply to its whole group.
- **Jev suggestions:** only for what local rules can't settle, and every answer cached. Course for a name (`lib/suggest/courseMatch.ts`, pure `guessCourse`: equal name ignoring accents/dots/Ea-Gy-Lab suffix, keyword or course code, one clearly closest name; different numbers never match; else `{ ask }`) feeds the defaults in `TimetableMappingDialog` and `DiscoveryDialog` through `useCourseSuggestions` (a confirmed Canvas mapping becomes a keyword, so it is never asked again). Grade components (M2 link dialog): `localDeadlineMatches` (`lib/suggest/componentMatch.ts`) adds a number guard between sibling components ("1. zh" / "2. zh") to `suggestDeadlineLinks`; only when it finds nothing does `ComponentLinkDialog` ask Jev which component each of the course's latest 20 deadlines belongs to. Duplicates: `borderlinePairs` (`lib/ical/dedupe.ts`) lists pairs whose titles are neither similar nor clearly different; `components/DuplicateCheck.tsx` asks about upcoming ones once per device and stores a "same" as a `CONFIRMED_PREFIX` ("=") entry in `ignoredDuplicatePairs` (a plain entry, the user's exception, always wins; `userExceptions` for counts). Server: `POST /api/javaslat` builds the questions itself (`lib/suggest/questions.ts`, no ids), `suggestWithJev` (`lib/server/jevSuggest.ts`) caches every answer for everyone under a hash of the question (`jevc:`, 30 days) and counts only uncached questions (`rl:jev:d:<userId>`, 150/day).
- **Due-change record:** the server keeps `chg:<userId>` (KV, `lib/server/dueChanges.ts`, pure `trackDueChanges`) so the 48 h "módosult" window starts when a move is first seen, not at every request. Seeded from the account's deadlines, pruned per render, deleted with the account.
- **Timetable (Neptun):** `ClassSession` / `TimetableSource` in `AppData` (not deadlines: never in urgency, radar, notifications or dedup). `lib/ical/neptun.ts` parses the static `.ics` (`<subject> ( - <group>) - <teachers> - <type>`); there is ONE calendar import, in `FeedSettings` (link or .ics file): content decides the route via `isNeptunCalendar` (Neptun → timetable import through `components/settings/useTimetableImport.tsx` and `TimetableSourceItem`; otherwise a normal `IcalFeed`, which needs a link). A file is parsed in the browser, only a link goes through `/api/ical`. Only the current week and later are imported (`timetableCutoff`/`upcomingSessions`: Monday 00:00 Budapest of this week; from `AppData.semester.start` when it is set and earlier), so past semesters are never asked about; a re-import keeps this semester's stored past sessions (back to the semester start, at most half a year: results refer to them). Subjects are mapped to courses once (`TimetableMappingDialog`, `subjectCourses`), the mapping survives re-imports; a subject can be mapped per Neptun group (key `subjectKey|group`, Ea and Gy as two courses, the default for new subjects with several groups); always resolve a session's course with `mappedCourse`, and apply dialog results with `applyMappingDecisions`. Export: view `?nezet=orarend`, `ExportOptions.includeClasses` (default off) for "összes"/course views; session UIDs derive from `sourceId` + `externalUid`. The data document carries `classSessions` (cap 1500); the server never re-fetches timetables. The home "Órák" toggle (`showClasses`) is a device preference, not in `AppData`.
- **Email digest (account-owned, opt-in):** pure selection in `lib/digest.ts` (`collectDigest` dedupes and picks open overdue ≤ 14 days + open deadlines from today to the end of this week (daily: at least tomorrow) / calendar month, `digestRange`; daily also lists today's `classesToday` from the account's timetable and `shouldSendDigest` only sends it when something is due today or tomorrow; `digestPeriodKey` per Budapest day / Monday week / month). The mails are rendered in `lib/digestEmail.ts` as the notice board (heading on felt, day strips with paper slips whose pin carries state, salmon overdue block, canary feed warning, stamped "Kritikus"/"Módosult"): table layout with inlined light tokens copied from `app/tokens.css` (the one other place raw hex is allowed, together with `lib/authEmail.ts`), a `<style>` block only for Archivo, a narrow-screen day column and the dark tokens under `prefers-color-scheme`. Server: `lib/server/digest.ts` (`dig:<userId>` = `{ frequency, unsubscribeKey, lastPeriod?, lastSentAt? }` + the `dig:index` set of userIds; **no confirmation step and no address of its own**: it goes to the account email, and only to users with `emailVerifiedAt`; `lastPeriod` so each period sends once; `runDigest(store, userId, now, appUrl, send?)` returns `sent|skipped|empty|removed|failed`, and removes the entry when the user is gone), `lib/server/email.ts` (Resend via fetch, env `RESEND_API_KEY`/`DIGEST_FROM`; logs in dev). Routes: `GET|PUT|DELETE /api/fiok/hirlevel` (session; no dependency on the calendar subscription), `POST /api/hirlevel` (form from the `/hirlevel` page and RFC 8058 one-click, params `m=leiratkozas&u=<userId>&k=<key>`; links only ever GET the page, never mutate), `GET /api/cron/hirlevel` (Vercel cron in `vercel.json`, `CRON_SECRET`). Live deadlines come from `loadLiveDeadlines`, shared with the .ics. Deleting the account deletes the digest. UI: `components/settings/DigestSettings.tsx` in the Értesítések tab.
- **Sync, offline, series:** every synced item (`courses` with their links/resources, `deadlines`, `customPlatforms`, `feeds`, `timetableSources`) carries `updatedAt`, stamped by the store's `trackChanges` wrapper around `set` (pure diff in `lib/sync/stamp.ts`, only items that really changed), so actions never stamp by hand; removals are recorded in `AppData.tombstones` (id → ISO, pruned at 60 days / 5000, `lib/sync/tombstones.ts`). Timestamps come from `syncNow()` (`lib/sync/clock.ts`): the device clock shifted by the offset to the server's `Date` header, so a wrong phone clock cannot decide who wins. `mergeAppData` (`lib/sync/merge.ts`) is field-level, latest-edit-wins (a tie goes to the remote) with the base deciding which side changed a field; a deletion beats an edit only if the edit is older than the tombstone; feed deadlines that two devices created under different ids are collapsed (`collapseFeedDuplicates`). Merge results and server data bypass the stamping (`rawSet`). The engine (`lib/sync/engine.ts`) also uploads on `pagehide`/tab hidden and retries on focus/visible. Offline: hand-written `public/sw.js` (registered by `ServiceWorkerRegister`, never for `/api/*`): static assets and icons cache-first, app pages network-first with a 4 s timeout and only plain 200s cached, offline falls back to that exact path, else the cached `/`; auth pages are network-only; the cache is cleared on sign-out via a message. Bump `VERSION` in `sw.js` when its logic changes. `app/manifest.ts` + `app/icon.tsx`/`apple-icon.tsx` (`lib/appIcon.tsx`) make it installable. Not browser-checked yet.
- **Several dates / recurring:** only when creating a manual deadline (`DeadlineForm`, tabs Egyszer · Több időpont · Ismétlődő; editing stays single-date). Pure logic in `lib/recurrence.ts`: `expandDueDates(first, RepeatSpec)` (sorted, de-duplicated by minute, at most `MAX_SERIES` = 30, `first` included; daily/weekly steps use date-fns on local dates so the wall-clock time survives DST, `until` includes the whole day, interval 1-52), `seriesTitles` ("Kvíz" → "Kvíz 1…n", "Kvíz 3" continues from 3). The store's `addDeadlines` (one `set`, one sync) gives more than one new deadline a shared `Deadline.seriesId` (informational; dedupe/export/radar ignore it); `removeDeadlines` removes several at once. The detail dialog shows "Sorozat: i/n" and offers Csak ezt / Ezt és a későbbieket on delete (`Dialog`, not `confirm()`).
- **Tests:** `npm test` runs `node:test` on `test/*.test.ts` (Node strips types; `test/alias-loader.mjs` resolves `@/` and extensions), with `TZ=UTC` on purpose (the server's zone). Fixtures are in `fixtures/ical`. Tests may only import modules free of React, zustand and `"use client"`.
- **Notifications:** pure logic in `lib/notifications.ts`, scheduler `components/NotificationScheduler.tsx` (only while a tab is open, no service worker); prefs and sent keys live in the store but are not part of `AppData`.
- **Privacy (GDPR):** the notice is `app/adatvedelem/page.tsx` (controller facts in `lib/legal.ts`). It is a legal statement: any change to what is stored, for how long, or which provider handles it updates the notice and `PRIVACY_UPDATED` in the same PR. Unconfirmed registrations expire after `PENDING_ACCOUNT_TTL_SECONDS` (user record and email index); confirming removes the expiry. Public pages (no session, no sync, no app chrome) are listed in `isPublicPath` (`lib/account/path.ts`) and in the `proxy.ts` matcher.
- **Course requirements:** the "Követelmények" section on the course page (`components/RequirementsSection.tsx`) holds `Course.requirements` (free text, capped at `MAX_REQUIREMENTS_CHARS` in `parseAppData`) and requirement documents, which are resources of kind `kovetelmeny`, hidden from `ResourceList`. The calendar and digest strip the text. Rules and results (M1): `AppData.requirementRules` (one validated `SubjectRules` per course, id `rules:<courseId>`, merged as one block by `mergeWhole`) and `AppData.requirementResults` (deterministic ids `courseId|componentId|instanceKey`, field-merged, capped at `MAX_REQUIREMENT_RESULTS`); types in `lib/rules/types.ts`, formulas parsed by `lib/rules/expr.ts`, `validateRules` (`lib/rules/validate.ts`, Hungarian errors) guards every import, `evaluate` (`lib/rules/engine.ts`) gives each grade's best/worst/status and gates, `solveFor` (`lib/rules/solve.ts`) answers "mi kell a jegyhez", templates in `lib/rules/fixtures.ts`; all pure. UI: `components/requirements/RulesPanel.tsx` (template picker, JSON editor, standing, flags, solver) and `ResultInputs.tsx`. Extraction (M3), the survey: `POST /api/kovetelmeny/elemzes` (`{ text, course: { name, code? } }`; same auth, verified email, 10/hour and 30/day limits as before) has Jev (TypeSafe System One, `systemOne` in `lib/server/jev.ts`, env `JEV_API_KEY`, model `SURVEY_MODEL` = `jev-latest`) read the whole document once: `buildSurveyRequest` (`lib/rules/extract/survey/questions.ts`) makes 24 independent typed questions (Noul for yes/no, Choice over fixed labels for structure and counts `n1`…`n15`, Choice over `none` + every number candidate for points, each `none` saying what it means; the wording is the owner's tested prompt, change it only after a live run against the fixtures; state fields `course` and `document`, at most `SURVEY_MAX_DOC_CHARS` = 40 000 characters). **Jev picks, code builds:** numbers are never generated, `numberCandidates` (`candidates.ts`, pure: ranges offered whole and as their ends, no years/dates/partial digit runs, at most 150) finds them and the answer is copied from the document. The raw answers are cached for everyone as `jevs:<sha256(request body) first 40 hex>` (30 days; labels and numbers only, never text) and the route returns `{ survey, truncated }`; 502 when Jev fails, 503 without a key. `readSurvey` (`read.ts`, pure, defensive about malformed answers) turns the answers into a `SurveyDraft` of fields (`value`, `flagged`, Hungarian `reasons`, `quote` = the candidate's context, `hidden`): flags from probabilities (`CHOICE_REVIEW_BELOW` 0.7, `NOUL_REVIEW_BAND` 0.25-0.8, wider on the yes side, `unclear` / `not_described` / `other` always), a number the text gives as an upper end ("74 pontig", candidate `upTo`) picked for a lower end (`UP_TO_REASON`), gates in `fields.ts` (`GATES`: a detail only counts if its structure answer says the part exists; a confident closed gate hides it, a doubtful one keeps the answer and flags "Attól függ, hogy …" only on details that carry a value; the grade limits are open for both point methods, raw points and component grades counted as points) and `consistency` checks (required value missing, min above max, limits not rising, mixed percent and points, limit above the total, components' sum differs from the stated total), which flag and never fix; `raw` is kept so thresholds can change without asking again. `surveyRules(values)` (`rules.ts`) builds `SubjectRules` from the confirmed form (`SurveyValues`, gates applied again), runs `validateRules` and `semanticErrors` (`extract/semantic.ts`) and gives Hungarian errors instead of rules when it cannot (grade by component grades, `other`, +/- scoring…); assumptions become "Ellenőrizd" rule flags. UI: `components/requirements/ExtractDialog.tsx` (a PDF drop zone or pasted text → a reading state → `SurveyForm.tsx` in an `xl` dialog: the form beside a sticky "Ezt állítjuk be" preview (`RulesPreview.tsx`, shared with the parser fallback and `TemplateReview`); a part's yes/no answer is the switch in its section heading; enums are visible radio lists, numbers a field with a pont/% toggle, the grade limits one 2–3–4–5 grid with a shared unit; flagged fields on canary paper with the quote and "Rendben", a "Következő" jump, saving blocked until nothing is unconfirmed and the rules are valid). When Jev is unavailable (503, 429, 502, network) the pattern parser `extractRules(text, answers)` (`lib/rules/extract/*`, pure, parser only: `text.ts` segments, `lexicon.ts` holds the Hungarian patterns, `assemble.ts` builds the rules and the questions the text leaves open) runs in the browser and its review (open questions, preview) is shown; if it rejects the text the form starts from `emptySurvey()` with a one-line reason. A PDF is read in the browser by pdf.js (`components/requirements/pdfText.ts`, legacy build; layout in `lib/rules/extract/pdf.ts`; `unwrapLines`) and never uploaded. Real Jev answers for five documents (answers, picked candidates, expected values; no text) are in `fixtures/kovetelmeny/jev-valaszok/` (`<doc>.json` from the owner's prompt run outside the app, `<doc>.app.json` from the app itself, checked through the browser on 2026-10-07), and `test/surveyRealAnswers.test.ts` holds the bar: no wrong field unflagged, the owner's set ≥ 107/115 right and ≤ 25 flags, the app's set ≥ 109/115 and ≤ 27. Fixture answers: `fixtures/kovetelmeny/<name>/survey.json` (the owner's expected-file format); eval against a real document with `npm run jev:survey -- <doc.txt> "<course>" [expected.json] [--dry]` (`scripts/jevSurvey.ts`, env `TYPESAFE_API_KEY` or `JEV_API_KEY`, prints raw answer, read value, flag and ✓/✗ per question). A result that fails `validateRules` or `semanticErrors` is never saved. Shared templates: `tpl:<university>:<code>:<semester>` in KV (pure logic `lib/rules/shared.ts`, storage `lib/server/ruleTemplates.ts`, routes `/api/kovetelmeny/sablon` and `/api/fiok/egyetem` for `uni:<userId>`); variants keyed by `rulesHash`, confirmers stored as hashed ids (`tplu:<userId>` indexes them so `deleteAccount` can remove them), notes stripped, the previous term offered as a fallback; the empty rules panel offers one before extraction (`components/requirements/SharedTemplate.tsx`). Every new pattern needs a fixture sentence in `fixtures/kovetelmeny/` and must keep `test/rulesExtract.test.ts` (grade equivalence with the templates) green. Never store results inside the rules, and never key results by index. The full tracker plan is in the project folder `plans/requirements-tracker/`.
- **Requirement links, catch-up, reminders (M2):** a component (or retake slot) is tied to the calendar by `RequirementRules.calendarLinks[componentId]` (`ComponentLink` in `lib/rules/links.ts`: `sessions` with a group/weekday/week selector and limit, `weeks`, or picked `deadlines` by `deadlineIdentity`; validated by `linksFrom`, kept when the rules are edited, never part of a shared template). `resolveInstances` (`lib/rules/instances.ts`) gives the instances with stable keys (`s:<Neptun UID>`, `w:<week>`, `d:<identity>`; single-result components always `n:1`), pins instances that have a result but are no longer selected, and marks those after the link's `since` as tracked. Week numbers come from `AppData.semester` (`lib/timetable/semester.ts`, Budapest Mondays; merged latest-edit-wins). `lib/catchup.ts` (pure, also used by the digest): `pendingInputs` (ended, tracked, no result; grouped per class or deadline), `awaitingResults` ("Még nincs eredmény", late after 14 days), `upcomingAssessments`, `shouldPrompt` against the account-wide `AppData.catchUp.promptedUntil` (merged as the later). UI: `components/catchup/CatchUpGate.tsx` (opens after this tab's first server pull, `pulledThisSession`, from `openCatchUp()` or `/?potlas=1`) + `CatchUpDialog.tsx`; `components/requirements/LinkedComponent.tsx`, `ComponentLinkDialog.tsx`, `InstanceInput.tsx` on the course page; `components/RemindersMenu.tsx` (header bell, `lib/reminders.ts`, nothing stored); a "Rögzítésre vár" block in the digest (`digestPendingFrom`; a daily mail also goes out for an unrecorded class since yesterday); an in-tab notice 30 min after the day's last linked class (`catchUpNotification`). Web Push is later (owner decision).
- **Settings page:** each section is its own component in `components/settings/`, rendered by `app/beallitasok/page.tsx` (the Naptárak tab holds `FeedSettings`, which also lists and imports Neptun timetables).
